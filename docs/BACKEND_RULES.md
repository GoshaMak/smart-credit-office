# Правила backend MVP — этап 0

Этот документ фиксирует решения перед реализацией. HTTP-схемы находятся в [openapi.yaml](openapi.yaml), общая схема — в [ARCHITECTURE.md](ARCHITECTURE.md). Новые маршруты к исходным 38 операциям не добавлены. Версия контракта 0.2.0 отражает уточнение схем до начала разработки клиентов.

## 1. Каталог и данные заявки

- Каталог содержит любое число продуктов, поддерживаемых текущим `LoanInput`. Произвольные новые поля нельзя добавить только конфигурацией: сначала расширяются схема API и валидация.
- `required_application_fields` — проверенные при загрузке каталога JSON Pointer к существующим полям `LoanInput`. Указатели на неизвестные поля/индексы, пустые или повторяющиеся требования отклоняются. Для документа требуется непустой код типа до 100 символов.
- Черновик можно создать с `data={}`. Через PATCH можно установить или сменить `product_id`, сумму, срок, цель и финансовые данные. PATCH с пустым `data` отклоняется. Поля отсутствуют — сохраняются; `null` отклоняется; переданный `financials` заменяется целиком и содержит все его обязательные поля.
- Формат переданных значений проверяется сразу. На подаче всегда нужны активный продукт, положительная сумма в его диапазоне и допустимый срок. Остальные обязательные поля и типы документов определяет каталог. Неизвестный продукт — 404, неполнота/нарушение его требований — 400.
- Подача фиксирует неизменяемый снимок данных компании, заявки, выбранных документов и внутренних требований продукта, согласия с actor/time. После подачи `product_id` не меняется. Изменения компании/каталога не меняют исторические снимки.
- Новый снимок уточнений содержит актуальный профиль компании на момент ответа, объединённые данные заявки, выбранные документы и прежние зафиксированные требования продукта. Новая ревизия запускает обе проверки и скоринг заново, даже если клиент уточнил только документ.
- В MVP предложение относится к исходному продукту и может менять сумму/срок в пределах требований снимка. Другой продукт требует отдельного изменения процесса и не предлагается скрыто через `terms.product_id`.
- `CompanyUpdate.legal_type` допустим только при соответствии длине неизменяемого ИНН; контрольные цифры ИНН в MVP не проверяются, чтобы сохранять синтетические сценарии задания.

## 2. Доступ и команды

JWT идентифицирует пользователя; роль и членство читаются из актуальной БД. `owner` и `representative` могут работать с заявками своей компании, включая имитацию подписания. Только owner изменяет профиль компании. Создание компании создаёт owner в той же транзакции. Пользователи, сотрудники и представители создаются seed-данными; регистрации и управления членством в MVP нет.

| Состояние | Действия клиента своей компании | Действия сотрудника банка | Действия системы |
| --- | --- | --- | --- |
| Draft | edit, upload_document, delete_document, submit | Нет доступа | Нет |
| Submitted | Чтение | Чтение | Начать проверки → Checking |
| Checking | Чтение | Чтение; retry_processing при blocked | Проверки → Scoring либо запрос данных → NeedsInfo |
| Scoring | Чтение | Чтение; retry_processing при blocked | Оценка → ManualReview либо запрос данных → NeedsInfo |
| NeedsInfo | upload_document, delete_document для новых файлов, answer_information_request | Чтение | Ожидание ответа; после ответа → Checking |
| ManualReview | Чтение | request_information, approve, reject | Нет кредитного решения |
| Offered | accept_offer, decline_offer | Чтение | Нет |
| Accepted | sign | Чтение | Нет |
| Signed | Чтение | Чтение; retry_processing при blocked | Имитация выдачи → Disbursed |
| Rejected / Declined / Disbursed | Чтение | Чтение | Нет |

`available_actions` и `available_bank_actions` — результат этих правил для конкретной роли. Дополнительные условия, например наличие удаляемых документов или открытого запроса, учитываются при расчёте. Банк получает пустой клиентский `available_actions`; клиент никогда не получает банковских действий. Правила повторно проверяются внутри команды.

Клиент читает только объекты компаний своего членства. Банк читает поданные заявки, их снимки, запросы и документы, включая общий маршрут скачивания; для Draft все банковские способы чтения возвращают 404. Вложенные ID проверяются вместе с ID заявки. Неверная глобальная роль либо попытка representative выполнить owner-действие своей компании — 403; отсутствие членства в компании объекта, чужой ID или скрытый объект — 404. Неверная версия/состояние, повторная подача или ответ — 409. Ошибки формы/значений — 400. Upload сохраняет специальные 413/415. Все ошибки соответствуют `Error`.

Изменения заявки, документов, уточнений и технического прогресса worker увеличивают `application.version`. Команды проверяют `expected_version` и состояние под блокировкой/CAS. Снимок имеет собственный последовательный `revision`, который не равен версии агрегата. Результат команды — состояние при commit; клиент перечитывает версию перед следующей командой.

## 3. Документы и уточнения

- Upload/delete доступны в Draft и NeedsInfo. Файлы PDF/JPEG/PNG до 10 MiB, не пустые; проверяется фактический объём и содержимое, а не только заявленный MIME. Исходное имя не участвует в ключе S3. Метаданные фиксируются только после успешной загрузки и повторной проверки версии/состояния.
- Один тип может иметь несколько документов. При первой подаче в снимок входят все доступные документы заявки. В ответе на уточнение `document_ids` — **полный набор** следующего снимка; ID уникальны и принадлежат этой заявке. Старый документ можно не включать в новый набор, сохранив его в истории.
- Удаление документа любого исторического снимка запрещено. Замена создаёт новый S3-объект и запись; существующий объект не перезаписывается. Новый незакреплённый документ можно удалить в Draft/NeedsInfo с проверкой версии.
- Требования нового снимка — объединение требований продукта и открытого запроса. Для каждого `required_document_types` запроса нужен документ с ID, которого нет в исходном снимке запроса. Ранее поданный документ не закрывает требование прислать новый. Все обязательные типы продукта также представлены в выбранном наборе.
- `requested_fields` запроса — только `/amount`, `/term_months`, `/purpose`, `/financials` или его существующие поля. Компания и продукт не уточняются через эти указатели. Хотя бы один указатель/тип документа обязателен. Запрошенные поля должны быть явно переданы в `answer.data`, финансовые данные — целым объектом. Значение может совпадать с прежним: факт подтверждения фиксируется ответом.
- Один открытый запрос на заявку. Банк создаёт его только из ManualReview; worker может создать из Checking/Scoring по типизированному ответу `needs_info`. Создание запроса и переход в NeedsInfo атомарны. Запрос хранит исходный `snapshot_id` внутренне, даже если публичная схема его не показывает.
- Ответ закрывает запрос, создаёт новый снимок и job, меняет состояние на Checking атомарно. Обновления обычным PATCH в NeedsInfo нет. Автоматического повторного использования старых оценок нет.
- Перед S3 upload создаётся строка `upload_reservations`, защищающая ключ объекта. Метаданные документа и снятие резервации коммитятся атомарно. Очистка блокирует старую резервацию и помечает её abandoned перед удалением объекта; поздняя загрузка не может записать документ после истечения резервации. Успешное удаление освобождает резервацию. Ошибки S3 оставляют удаляемый tombstone/reservation для повторной очистки.
- Очистка S3 удаляет только объекты префикса `documents/`, не имеющие метаданных или активной резервации и старше 10 минут; сбои очистки допускают повтор. Объекты исторических снимков исключены из удаления.

## 4. Jobs и технические статусы

Очередь находится в PostgreSQL. Захват через `FOR UPDATE SKIP LOCKED` выдаёт lease и уникальный идентификатор захвата. Внешний вызов — вне транзакции захвата. Commit результата проверяет владельца/срок lease, текущий снимок и допустимое состояние. Старый worker не может завершить заново захваченное задание. Результат, события, статус и следующее задание сохраняются атомарно.

Ключ логического шага: `(application_id, snapshot_id, step, source)`, где source нужен для ФНС/БКИ. Вызовы ФНС и БКИ выполняются последовательно, затем скоринг. request_id создаётся и сохраняется до первого вызова; он стабилен для всех повторов того же шага, в том числе ручного возобновления. Изменение входа требует нового снимка. Повторная доставка или возобновление не пересчитывают успешный шаг.

| Бизнес-состояние | `processing.stage` | `processing.status` |
| --- | --- | --- |
| Draft / NeedsInfo | `processing` отсутствует | Активной обработки нет |
| Submitted | checks | queued |
| Checking | checks | queued / running / retry_scheduled / blocked |
| Scoring | scoring | queued / running / retry_scheduled / blocked |
| ManualReview / Offered / Accepted / Rejected / Declined | decision | completed |
| Signed | disbursement | queued / running / retry_scheduled / blocked |
| Disbursed | disbursement | completed |

`attempt` — число начатых вызовов текущего шага/источника за всю его историю, включая ручные повторы; в очереди до первого вызова и на decision равно 0. `next_retry_at` есть только при retry_scheduled. `error_code` — только у retry_scheduled/blocked. `retry_available=true` только для blocked в Checking/Scoring/Signed, без активного job, когда техническая причина допускает явное возобновление. Клиентская карточка не содержит `processing`.

Начальная конфигурация: timeout адаптера 5 секунд, lease 30 секунд, три попытки за автоматический цикл (включая первую), задержки 1 и 5 секунд. Ошибка подключения, timeout и HTTP 503 повторяемы. Некорректный ответ/несовпадение request_id или snapshot_id и конфликт request_id/input — blocked сразу. Содержательные результаты и needs_info не повторяются автоматически. Эти параметры настраиваются окружением; lease должен превышать timeout с запасом.

После исправления технической причины сотрудник вызывает retry-processing. Команда под блокировкой создаёт новый цикл только незавершённого шага текущего снимка; счётчик общих попыток не обнуляется, лимит автоматического цикла начинается заново, actor/основание системного действия фиксируются. Ручной повтор поддерживает и Signed; успешную оценку или завершённую заявку он не меняет.

`sign` выполняет Accepted → Signed и создаёт job выдачи. Worker имитирует выдачу, фиксирует уникальный результат по ключу шага и Signed → Disbursed; повтор не создаёт второго события выдачи. Внешних денежных операций нет.

## 5. Внутренний контракт локальных адаптеров

Это локальный контракт для будущего `integration-mock` и заглушки скоринга; он не добавляет публичных маршрутов. Схемы нормализованных результатов ФНС/БКИ опубликованы как `FnsCheckResult`/`BkiCheckResult` в OpenAPI. Никакие реальные сервисы и данные не используются.

### Общий envelope

Локальные проверки: `POST /v1/checks/fns`, `POST /v1/checks/bki`. Запрос содержит `request_id` (UUID), `snapshot_id` (UUID), `schema_version="1"`, `company` (снимок Company), `data` (LoanInput), `product` (зафиксированный Product), `document_types` (уникальные строки выбранного набора). Скоринг: `POST /v1/scoring`; те же поля плюс `checks` с нормализованными `fns` и `bki`.

Во всех схемах запрещены неизвестные поля и `null`. Ответы:

| HTTP / `status` | Поля помимо status | Обработка |
| --- | --- | --- |
| 200 / succeeded | request_id, snapshot_id, schema_version="1", result | Сохранить содержательный результат |
| 200 / needs_info | request_id, snapshot_id, schema_version="1", requested_fields, required_document_types, message | Создать InformationRequest, остановить цепочку |
| 503 / technical_error | request_id, snapshot_id, schema_version="1", error_code, retryable=true | Ограниченный технический повтор |
| 409 / technical_error | request_id, snapshot_id, schema_version="1", error_code=REQUEST_INPUT_CONFLICT, retryable=false | Blocked, требуется исправление |

Таймаут представлен отсутствием своевременного ответа; адаптер нормализует его в `TIMEOUT`. `needs_info` имеет те же ограничения требований, что InformationRequestCreate, без expected_version. Результат ФНС/БКИ обязан совпадать со source, envelope обязан повторять ID и версию запроса; нарушение — `INVALID_RESPONSE`, не содержательный риск. В CheckRun для недостаточности данных используется status=needs_info без result/error_code; результаты есть только у succeeded, технические error_code/retryable — только у failed.

Вход канонизируется как JSON с отсортированными ключами и без пробельных разделителей, UTF-8, `ensure_ascii=false`, `allow_nan=false`; деньги остаются строками, даты/UUID — контрактными строками. Массивы с семантикой множества (document_types, reason_codes) сортируются до первого вызова; сохранённый вход повторно не собирается из изменяемых справочников. SHA256 полного входа, включая идентификаторы, хранится с request_id. Для того же request_id и входа успешный/needs_info ответ неизменен; другой вход даёт 409. Временная ошибка не кэшируется как успех. Повторённый успешный ответ не содержит нового времени или случайных значений; timestamp ScoringResult назначается backend при первом сохранении.

### Синтетические сценарии

Сценарий выбирается серверной fixture по синтетическому ИНН; публичного флага выбора/подмены результата нет. Неизвестный ИНН получает обычный успешный сценарий. `not_found` и `unavailable` принципиально различны.

| Fixture ИНН | Сценарий |
| --- | --- |
| 0000000001 | ФНС active/matches, БКИ без просрочек, успешный скоринг |
| 0000000002 | ФНС: company_found=false, status unknown, регистрация не совпала; succeeded с COMPANY_NOT_FOUND |
| 0000000003 | ФНС: неактивная компания, REGISTRATION_INACTIVE |
| 0000000004 | ФНС: регистрационное расхождение/недостоверность, REGISTRATION_MISMATCH и UNRELIABLE_DATA |
| 0000000005 | БКИ: просрочка 100000.00 RUB, max_overdue_days=45, OVERDUE_OBLIGATIONS |
| 0000000006 | БКИ: history_found=false, нулевые наблюдаемые показатели, NO_CREDIT_HISTORY |
| 0000000007 | ФНС: первый вызов 503 SOURCE_UNAVAILABLE, следующий успешен |
| 0000000008 | ФНС: первые три вызова TIMEOUT, следующий успешен после ручного возобновления |
| 0000000009 | БКИ: needs_info с /financials и финансовой отчётностью, пока в текущем снимке нет financial_statement; новая ревизия с документом успешна |

Обычная fixture ФНС: company_found=true, business_status=active, registration_matches=true, unreliable_data=false, reason_codes=[]. Обычная fixture БКИ берёт задолженность/платежи из financials при наличии, иначе наблюдаемые нули; overdue_amount=0.00, max_overdue_days=0, history_found=true, reason_codes=[]. Технический счётчик попыток fixture живёт в локальном сервисе; перезапуск mock сбрасывает его. Это демонстрационное допущение, а не гарантия очереди. Тесты временного сбоя не перезапускают mock между попытками.

### Скоринг stub-v1

Обязательны два успешных нормализованных результата проверок и полный `financials`; отсутствие financials возвращает needs_info с `/financials`, без кредитного решения. Backend не вызывает скоринг до завершения проверок. Fixture не переопределяет переданные финансовые данные скрытыми случайными значениями.

`score` — целое число 0..100, больший балл означает больший риск; `scale="risk_0_100_higher_is_riskier"`, `model_version="stub-v1"`. Базовый балл 20. Независимые добавки:

| Условие | Баллы | Factor |
| --- | --- | --- |
| monthly_revenue <= monthly_expenses | +30 | NON_POSITIVE_OPERATING_MARGIN |
| monthly_debt_payments > 30% monthly_revenue | +20 | HIGH_DEBT_PAYMENTS |
| outstanding_debt > 6 × monthly_revenue | +15 | HIGH_OUTSTANDING_DEBT |
| ФНС company_found=false | +40 | COMPANY_NOT_FOUND |
| Компания найдена, business_status != active | +30 | REGISTRATION_INACTIVE |
| Компания найдена, registration_matches=false | +20 | REGISTRATION_MISMATCH |
| ФНС unreliable_data=true | +20 | UNRELIABLE_DATA |
| БКИ overdue_amount > 0 или max_overdue_days > 0 | +30 | OVERDUE_OBLIGATIONS |
| БКИ history_found=false | +10 | NO_CREDIT_HISTORY |

Сумма ограничивается сверху 100; factors — уникальные коды сработавших условий, отсортированные лексикографически. Сравнения выполняются Decimal, в том числе при нулевой выручке, без деления. В result заглушки: model_version, score, scale, factors. Backend добавляет id, snapshot_id, request_id, created_at при сохранении ScoringResult. Модель не создаёт CreditDecision и не выбирает условия кредита.

### Демонстрационная политика manual-v1

`CREDIT_POLICY_VERSION=demo-manual-v1` считывается из серверной конфигурации, фиксируется в каждом решении и не принимается из HTTP-запроса. Сотрудник задаёт непустые reason_codes, internal_comment, client_message. Начальный набор оснований: MANUAL_APPROVAL, REDUCED_AMOUNT, SHORTER_TERM, HIGH_DEBT_BURDEN, REGISTRATION_RISK, CREDIT_HISTORY_RISK; новые непустые коды допустимы и остаются внутренними данными банка.

Системные ограничения одобрения: ManualReview, успешные обязательные проверки и скоринг **текущего** снимка, отсутствие открытого запроса/активного job, допустимые условия исходного продукта. Содержательные флаги риска доступны сотруднику; автоматического порога одобрения/отказа нет. CreditDecision.source всегда manual, автор — текущий сотрудник. Отказ доступен только в ManualReview. Предложение и решение создаются атомарно, одно действующее предложение на заявку.

## 6. JWT, refresh и аудит

- Access: HS256, ровно 120 секунд от iat, `sub=user UUID`, `sid=session UUID`, `jti=token UUID`, `iss=credit-backend`, `aud=credit-api`, iat/nbf/exp в NumericDate, nbf=iat. Алгоритм задан сервером; значения из заголовка токена не выбирают ключ/алгоритм.
- Секрет `JWT_SECRET` передаётся окружением, минимум 32 случайных байта (base64 в конфигурации); отсутствующий/короткий секрет останавливает старт. В репозитории только placeholder и явно локальная инструкция генерации. Issuer/audience настраиваются окружением согласованно для выдачи/проверки. Вне локального режима используется HTTPS.
- На каждом защищённом запросе проверяются claims, активность и абсолютный срок сессии, затем текущие права. Роль/членство из JWT не используются как источник полномочий. Истёкшая сессия запрещает доступ даже ещё действующего JWT.
- Refresh — 32 случайных байта в base64url, в БД SHA256, без открытого значения. Сессия живёт ровно 48 часов от входа; ротация не продлевает срок. Сохраняется история погашенных хешей. Reuse отзывает сессию с отдельным commit до возврата 401.
- Ротация/logout синхронизируются блокировкой строки сессии и проверкой хеша/сроков. Logout отозванного/неизвестного токена безопасно возвращает 204 и не влияет на другие сессии. Logout с известным погашенным refresh также отзывает его сессию.
- Все auth-ответы имеют Cache-Control: no-store. Веб-клиент передаёт access через Bearer, refresh — телом по существующему контракту, выполняет единственный refresh одновременно; после неопределённого результата refresh требуется новый вход. Конкретное хранилище токенов веб-клиента относится к frontend-интеграции; backend не вводит cookie-механику на этом этапе.
- Аудит: actor_type (client/bank_employee/system), actor_id при наличии, action, object_type/id, result (success/denied/failure), request_id/job_id, timestamp UTC, изменённая версия/снимок и безопасные коды оснований. Запись успешной бизнес-операции в той же транзакции; отказ/ошибка записываются отдельно от её rollback.
- Журналируем login/refresh/reuse/logout, создание/изменение компании, черновика, upload/delete/download, submit, запрос/ответ уточнений, шаги worker/повторы, решение, принятие/отклонение, подписание/выдачу и запреты доступа. Не журналируем пароли, JWT/refresh, секреты, содержимое документов и полный payload финансовых данных; клиентская история отделена от внутреннего аудита.

## 7. Проверка контракта

Из корня репозитория:

```sh
uv run --project backend --locked python tools/validate_contract.py
uv run --project backend --locked python -m pytest tools/tests
uv run --project backend --locked python -m pytest backend/tests/test_documents_unit.py
uv run --project backend --locked python -m credit.cleanup
```

Проверка отклоняет дубли YAML-ключей, невалидный OpenAPI 3.1, несовпадения примеров со схемами и отсутствие no-store у auth-ответов. При изменении схем выполняются регрессионные проверки разрешённого выбора продукта, запрета его смены в уточнениях и новых технических состояний.

Использованные первичные источники: [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0.html), [openapi-spec-validator](https://openapi-spec-validator.readthedocs.io/en/latest/python.html), [PyYAML](https://pyyaml.org/wiki/PyYAMLDocumentation). Технические результаты Python/sqlc/PostgreSQL и точные версии фиксируются отдельно в backend.

## 8. Решения по доступу к БД и миграциям

Python-плагин sqlc генерирует async-методы на SQLAlchemy Core, выполняющие исходный SQL; ORM-сущности и сессии SQLAlchemy ORM не вводятся. Бизнес-операция получает async connection из общего пула и управляет транзакцией; все сгенерированные querier внутри операции используют это соединение. JSONB-параметры оборачиваются в `psycopg.types.json.Jsonb` на границе репозитория, поскольку генератор оставляет для них `Any`. Сгенерированные файлы не исправляются вручную.

Для дальнейших миграций выбираем нумерованные SQL-файлы и небольшой Python runner на том же драйвере: таблица schema_migrations с версией/checksum/временем, session advisory lock на время применения, каждый файл и запись версии в одной транзакции. Несовпадение checksum уже применённого файла останавливает запуск. sqlc читает те же SQL-файлы; шаги, несовместимые с транзакцией, в MVP не вводятся. Runtime API/worker не применяют миграции автоматически: отдельная init-команда завершает их до готовности процессов. Сам runner и предметная схема относятся к этапам 1–2; на этапе 0 проверена минимальная SQL-миграция тестовой таблицы.
