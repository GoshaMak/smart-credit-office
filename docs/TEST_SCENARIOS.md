# Приёмочные сценарии backend

Данные тестовые и полностью синтетические. Сценарии проходят через HTTP с ролью клиента или сотрудника; между командами клиент перечитывает заявку и берёт актуальную `version`. Worker обрабатывает задания в PostgreSQL, а проверки вызывают локальный `integration-mock`. Для хранения файлов нужен S3/LocalStack.

## Подготовка и основной путь

Из корня после старта локального Compose выполнить `uv run --project backend --locked python -m credit.seed` (или команду из README). Seed создаёт:

| Логин | Пароль | Роль |
| --- | --- | --- |
| client | demo-client-password | client, owner собственной компании |
| representative | demo-representative-password | client, representative компании клиента |
| other | demo-other-password | client, отдельная компания без общего членства |
| banker | demo-bank-password | bank_employee |

Seed повторяем: повторный запуск не меняет пароль активного пользователя, не клонирует компании/продукты, создаёт S3 bucket при необходимости. Каталог содержит как минимум два продукта с разными суммами, сроками и документами.

1. Войти как client и получить текущего пользователя, членства и доступные продукты. Проверить `Cache-Control: no-store`.
2. Создать пустой черновик для своей компании. Установить продукт, сумму/срок и цель PATCH; установить financials. Попытка изменить неактуальную версию даёт 409.
3. Загрузить PDF финансовой отчётности. Проверить прирост версии, список метаданных и побайтовое совпадение скачанного файла. Попытка подать заявку без обязательного продукта или документа даёт 400; заявка остаётся Draft.
4. Подать заявку с двумя согласиями и актуальной версией. Повторная подача даёт 409, новых снимков/jobs не создаёт. Банк не видит черновик. В рабочей очереди поданная заявка появляется без внутренних полей.
5. Worker последовательно выполняет ФНС, БКИ и scoring `stub-v1`. Проверить результаты на карточке банка и состояние ManualReview. Доступ к чужой компании и документу возвращает 404.
6. Сотрудник одобряет заявку с альтернативной суммой или сроком того же продукта. Проверить сохранённое ручное решение, автора, `policy_version`, внутренний комментарий, сообщение клиенту и terms предложения. Клиент видит только публичное сообщение, не банковские данные.
7. Клиент принимает предложение, представитель компании выполняет имитацию подписания. Worker переводит Signed в Disbursed. Повторные accept/sign команду отклоняют, второго результата выдачи/события нет.

## Варианты процесса и ошибок

| Сценарий | Действия | Ожидаемый результат |
| --- | --- | --- |
| Предложение отклонено клиентом | Провести заявку до Offered, вызвать decline | Declined, предложение закрыто, повторный ответ 409 |
| Ручной отказ | Провести другую заявку до ManualReview, вызвать reject с основанием | Rejected; клиент видит `client_message`, сотрудник видит только ему доступные основания и комментарий |
| Запрос данных сотрудником | ManualReview → request_information с `/financials` и `financial_statement` | NeedsInfo, один открытый запрос, клиентский `available_actions` содержит answer |
| Ответ на уточнение | Загрузить новый документ, ответить полным `document_ids`, передать целиком financials | Запрос закрыт; новый revision/current_snapshot_id; новый цикл checks/scoring; исторический документ старой версии доступен по прежнему ID |
| Подтверждение без изменения суммы | Передать указанное поле с тем же значением | Ответ принят и отражён новой ревизией |
| Невалидное уточнение | Передать продукт вместо разрешённого поля, пустое тело данных, неизвестный/чужой document ID или повторный запрос | 400 для схемы/недостающего требования, 404 для чужого вложенного ID, 409 для закрытого запроса/конфликтной версии; транзакция без частичного снимка |
| Отсутствие компании в синтетическом ФНС | Использовать fixture `0000000002` | CheckRun succeeded с company_found=false; банку показан фактор риска. Это не технический сбой и не автоматический отказ |
| Временная ошибка ФНС | Fixture `0000000007` | Сначала failed/retry_scheduled, затем успешно после повтора; бизнес-статус остаётся Checking |
| Исчерпание попыток | Fixture `0000000008` | После 3 автоматических попыток blocked/retry_available; событие не раскрывает клиенту технический код; retry-processing создаёт только повтор той же незавершённой операции |
| Worker перезапущен с незавершённым job | Остановить обработку после lease, дождаться истечения/передать следующему runner | Job повторно захвачен; результаты и события идемпотентны; старый claim не может выполнить commit |
| Два конкурирующих worker | Одновременно захватывают доступные задания | Одно задание захватывается одним worker; нет двойного результата/перехода |
| Конкурентное редактирование | Две команды с одинаковым expected_version | Ровно одна успешна, другая получает 409 |
| Refresh reuse | Login, refresh, повтор старого refresh, затем попытка использовать access | Reuse возвращает 401/no-store и отзывает сессию; новый access больше не работает |
| Раздельные сессии | Два login, logout одной сессии | Отзывается ровно одна сессия; вторая остаётся активна |
| Инъекция повреждённого файла | MIME разрешён, magic bytes не PDF/JPEG/PNG | Upload отклонён; версия и метаданные БД не меняются, объект удаляется или попадает в безопасную очистку |
| Конкурентная подача во время upload | Во время записи S3 выполнить submit с текущей версией | Финальная фиксация метаданных получает 409; исторический снимок неизменяем, временный объект очищается |

## Проверка безопасности и эксплуатационных ответов

- Для каждой роли отдельно проверить GET/PATCH/команды заявки и download: чужая компания, чужой document ID, document ID от другой заявки, Draft у банка, representative на owner-only PATCH.
- Для отказов схем, прав и состояния проверять точные HTTP-код и `{message, details}`. Auth-вход, refresh, logout, `/auth/me` и их ошибки всегда имеют `Cache-Control: no-store`.
- Клиентские ответы не содержат `processing`, CheckRun, ScoringResult, `internal_comment`, `reason_codes`, `author_id`, S3 bucket/key, access/refresh секреты. Внутренний audit и логи не содержат пароли, токены или содержимое документов.
- Проверить `/health/live` без зависимости от БД, `/health/ready` с текущими миграциями. Отказ mock не должен делать API readiness unhealthy.
- Перезапуск API/worker сохраняет PostgreSQL и S3 данные. Проверить cleanup только на объекте без метаданных старше защитного интервала; старые документы снимков остаются.

Автоматические тесты лежат в `backend/tests`; проход демонстрации по HTTP описан `tools/demo.py`. Схема вызовов всех 38 операций дана в [requests.http](requests.http). Интеграционные проверки должны указывать на отдельную тестовую PostgreSQL и отдельный bucket LocalStack; они никогда не пересоздают или очищают произвольную БД.

Для полного интеграционного набора поднимите изолированные сервисы (PostgreSQL на `55443`, LocalStack на `4567`):

```sh
docker compose -p credit-backend-integration -f backend/compose.integration.yaml up --detach --wait
DATABASE_URL='postgresql+psycopg://credit_test:credit-test-local-only@127.0.0.1:55443/credit_test' \
  uv run --project backend --locked python -m credit.migrate
TEST_INTEGRATION=1 \
TEST_DATABASE_URL='postgresql+psycopg://credit_test:credit-test-local-only@127.0.0.1:55443/credit_test' \
TEST_DATABASE_CONFIRM=credit_test \
TEST_S3_ENDPOINT='http://127.0.0.1:4567' \
TEST_DOCUMENT_BUCKET='credit-tests-local' \
  uv run --project backend --locked python -m pytest backend/tests/test_database_integration.py
docker compose -p credit-backend-integration -f backend/compose.integration.yaml down
```

PostgreSQL data is held in container tmpfs and removed when the project is brought down. The test code rejects any database other than the explicitly confirmed `credit_test` and any non-local S3 endpoint.
