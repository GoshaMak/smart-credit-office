# План реализации backend

## Основания и границы

План составлен по [заданию](task.pdf), [архитектуре](ARCHITECTURE.md) и [OpenAPI](openapi.yaml). На момент первоначального планирования `backend/` был пуст; HTTP-контракт содержит 38 операций. Текущий статус основных этапов см. в [DELIVERY_STATUS.md](DELIVERY_STATUS.md).

Реализуем backend: REST API для клиента и сотрудника банка, PostgreSQL, worker, хранение документов в S3, локальные интеграционные заглушки, тесты и воспроизводимый запуск. Веб-интерфейсы остаются за пределами этого плана; взаимодействие с backend проверяется HTTP-запросами и автоматизированными сценариями. В полном решении из PDF веб-интерфейс должен предоставить другой участник команды.

Сохраняем заданный стек: uv, Python 3.14, FastAPI, sqlc, JWT HS256, PostgreSQL 16, S3 через LocalStack. Приложение — модульный монолит с отдельным процессом worker. Не добавляем брокер сообщений, реальные интеграции ФНС/БКИ, ML-сервис, реальные подпись и переводы денег. Все демонстрационные данные синтетические.

Порядок работы: уточнение контракта → рабочее окружение → схема БД → доступ и справочники → черновики и документы → обработка → ручное решение и выдача → уточнения и восстановление → итоговая проверка и сдача. Проверки каждого блока выполняются при его реализации.

## 2. Спроектировать БД, миграции и транзакционные границы

Подготовить ER-диаграмму, миграции и SQL-запросы. Сгенерированный sqlc-код не редактировать вручную; управление транзакциями остаётся в бизнес-операциях.

| Группа | Таблицы и ключевые ограничения |
| --- | --- |
| Доступ | `users`, `auth_sessions`, `refresh_tokens`: уникальный login, уникальный хеш токена, срок сессии, признаки погашения и отзыва |
| Компании и продукты | `companies`, `company_members`, `loan_products`: уникальные ИНН и код продукта, уникальное членство, версия компании, согласованные диапазоны суммы/срока |
| Заявки и снимки | `applications`, `application_snapshots`: версия агрегата, текущий снимок, уникальный номер ревизии в заявке, неизменяемые данные компании/заявки/требований продукта |
| Документы | `documents`, связи снимков с документами: уникальный ключ S3, метаданные, выбранный набор документов, запрет удаления объектов исторических снимков |
| Уточнения | `information_requests`: не более одного открытого запроса на заявку, связь ответа с новой ревизией |
| Проверки и решения | `check_runs`, `scoring_results`, `credit_decisions`, `offers`: привязка к снимку, история попыток, уникальность успешного результата логического шага, `source=manual`, не более одного действующего предложения |
| Процесс | `jobs`, `application_events`, `audit_events`: ключ дедупликации задания, lease, попытки, время следующего запуска, actor и корреляционные идентификаторы |

- Денежные значения хранить как точный `NUMERIC`, в Python использовать Decimal, в API — десятичные строки; валюта RUB. Время — `timestamptz`/UTC.
- Добавить FK и проверки принадлежности: снимок/документ/предложение должны относиться к указанной заявке. Важные инварианты закрепить ограничениями БД, а не только HTTP-валидацией.
- Добавить индексы для списков по компании/статусу, членства, истории и выдачи готовых заданий. Сортировка и offset-пагинация соответствуют OpenAPI.
- Снимок включает подтверждённые согласия, автора и время подачи во внутренней модели. Изменение профиля компании не меняет уже поданные снимки.
- Любая мутация существующей заявки синхронизируется через её версию и допустимое состояние; новая версия, событие, аудит и создаваемое задание фиксируются вместе.

**Готовность:** схема разворачивается с нуля; ограничения и откат транзакций проверены на PostgreSQL 16; SQL-генерация воспроизводится.

## 3. Реализовать доступ, компании и каталог

HTTP-группы: `/auth/*`, `/companies*`, `/products*`.

- Вход по подготовленным пользователям с безопасным хешированием паролей. Регистрацию, восстановление пароля и управление сотрудниками не добавлять: в контракте таких операций нет.
- JWT HS256 на 2 минуты; абсолютная сессия на 2 дня. На защищённых запросах проверять подпись, claims и активность `sid`.
- Refresh token — случайный непрозрачный секрет; в БД только хеш. Ротация атомарная, старые хеши сохраняются до окончания сессии, повторное использование отзывает всю сессию.
- Синхронизировать ротацию и logout блокировкой сессии. Отзыв при повторном использовании должен сохраниться даже при возврате 401; его нельзя откатить обработкой ошибки.
- Logout идемпотентно отзывает одну сессию. Все auth-ответы, включая ошибки, получают `Cache-Control: no-store`.
- Проверять роль и членство сервером. Для чужих объектов возвращать 404 по контракту; запрет роли/действия — 403.
- Создание компании атомарно создаёт членство `owner`; изменение доступно owner с проверкой версии. ИНН неизменяем и соответствует типу юрлица/ИП по длине.
- Каталог задавать начальными данными/конфигурацией, без жёсткого списка продуктов в коде. API управления каталогом и членством не добавлять; представителей включить в seed.

**Готовность:** работают обе роли и несколько компаний; нельзя получить чужие данные. Проверены конкурентная ротация, reuse, logout, абсолютное истечение и независимость разных сессий.

## 4. Реализовать черновики и документы

HTTP-группы: создание/чтение/PATCH/списки `/applications`, `/documents*`, история `/events`.

- Поддержать неполные черновики, частичные обновления и замену `financials` целиком; отклонять `null` и неизвестные поля согласно схемам.
- Централизовать проверки состояния, версии и прав; из тех же правил рассчитывать `available_actions`. Отображаемое действие не заменяет повторной проверки при команде.
- Различать проверку формата при сохранении и проверку полноты/ограничений продукта при подаче.
- Принимать файлы через FastAPI: PDF/JPEG/PNG, до 10 MiB. Проверять фактический объём и допустимость содержимого, генерировать уникальный S3 key; передавать данные без блокирующего I/O в event loop.
- После успешной загрузки фиксировать метаданные и увеличение версии в БД. Перед фиксацией повторно проверять версию/состояние: загрузка S3 могла завершиться уже после конкурентной подачи заявки.
- Скачивание проксировать после проверки доступа, с безопасным `Content-Disposition` и `Cache-Control: no-store`. Bucket/key и реквизиты S3 не возвращать.
- Удалять только документы, не включённые ни в один снимок. Замена — новый документ; исторические файлы неизменяемы.
- Предусмотреть очистку S3-объектов без метаданных и завершение удаления после сбоя. Очистка учитывает незавершённые загрузки и период ожидания, чтобы не удалять используемые объекты.

**Готовность:** клиент сохраняет черновик, загружает/скачивает документы и видит актуальную версию. Проверены чужие document ID, лимиты файлов, конфликт загрузки с submit и недоступность S3.

## 5. Реализовать подачу, очередь и автоматические шаги

HTTP: `/applications/{id}/submit`; внутренние шаги проверок и скоринга.

- В одной транзакции проверить доступ, `Draft`, `expected_version`, продукт, обязательные поля, документы и согласия; создать снимок, событие и job, перевести в `Submitted`.
- Повторную подачу отклонять с 409; не создавать второй снимок и вторую цепочку обработки.
- Реализовать захват job через `FOR UPDATE SKIP LOCKED` в короткой транзакции. Внешние вызовы выполнять после её завершения.
- У job хранить lease, номер попытки, время запуска и идентификатор захвата. Просроченное задание доступно новому worker; старый worker после потери lease не может зафиксировать результат.
- Дедуплицировать логический шаг по заявке/снимку/типу шага/источнику. Вызовы адаптеров получают стабильный идентификатор; повторная доставка не создаёт повторных эффектов.
- Проверять актуальность снимка перед фиксацией результата. Результат, смена состояния, событие и следующий job сохраняются атомарно.
- Реализовать локальные ФНС/БКИ: успешный ответ, содержательные расхождения/риски, отсутствие компании, недостаточность данных, временная ошибка, таймаут и восстановление. Способ выбора сценария определяется синтетическими fixtures, не скрытым production-параметром API.
- Реализовать адаптер скоринга и детерминированный `stub-v1`. Сохранять входную версию/идентификаторы, шкалу и факторы. Один request ID с другим входом не должен молча менять прежний результат.
- Успешная цепочка: `Submitted → Checking → Scoring → ManualReview`. Содержательный отрицательный результат проверки остаётся данными для сотрудника; автоматических кредитных решений нет.
- Повторы выполнять только для технических ошибок по конфигурации timeout/backoff/лимита попыток. После исчерпания — `blocked`, без кредитного отказа.

**Готовность:** поданная заявка доходит до ручного рассмотрения; два worker не дублируют эффекты. Перезапуск и повторная доставка не теряют задания и не применяют устаревшие результаты.

## 6. Реализовать банковское рассмотрение и завершение выдачи

HTTP-группы: `/bank/applications*`, `/approve`, `/reject`, `/offers*`, `/sign`.

- Реализовать очередь без черновиков, фильтры, карточку, версии снимков и чтение документов. Проверки/скоринг карточки относятся к текущему снимку; решения содержат историю с привязкой к снимкам.
- Разделить банковские и клиентские DTO. Клиент получает `PublicDecision` и безопасную историю; внутренние комментарии, причины риска, результаты проверок и технические ошибки ему не передаются.
- Одобрение разрешено только в `ManualReview` при завершённых обязательных проверках и скоринге текущего снимка. Проверить условия продукта; атомарно создать ручное решение, предложение, события и статус `Offered`.
- Сохранять автора, основания, версию политики, внутренний комментарий и отдельное сообщение клиенту. Отказ также только ручной из `ManualReview`.
- Поддержать альтернативную сумму/срок в `Offer.terms`, принятие и отклонение только актуального предложения своей заявки с проверкой версии.
- `accept`: `Offered → Accepted`; `decline`: `Offered → Declined`; `sign`: `Accepted → Signed` и задание имитации выдачи; worker: `Signed → Disbursed`.
- Конкурирующие approve/reject и accept/decline дают ровно один результат. Повторный job выдачи не создаёт повторных событий выдачи.

**Готовность:** первый сквозной HTTP-сценарий проходит от входа до `Disbursed`. Отдельно проходят ручной отказ, альтернативные условия и отказ клиента от предложения.

## 7. Реализовать уточнения и ручное восстановление

HTTP-группы: `/information-requests*`, `/answer`, `/retry-processing`.

- Сотрудник из `ManualReview` создаёт один открытый запрос с JSON Pointer полями, типами документов и сообщением; заявка переходит в `NeedsInfo`.
- Системный запрос недостаточности данных использует согласованные на этапе 0 правила и ту же сущность. Невалидные указатели нельзя сохранять как невыполнимое требование клиенту.
- В `NeedsInfo` разрешить добавление необходимых документов. Данные уточняются через ответ на запрос; обычный PATCH остаётся командой черновика.
- Ответ проверяет версию, открытый запрос, полноту объединённых данных и выбранный набор документов. Новые данные, закрытие запроса, новый снимок и задание проверки фиксируются атомарно; переход — `NeedsInfo → Checking`.
- Проверки и скоринг для нового снимка запускаются заново; старые результаты сохраняются как история и не разрешают одобрение новой версии.
- `/retry-processing` доступен сотруднику только для восстанавливаемого технического сбоя текущего снимка. Он не меняет данные или бизнес-статус произвольно, не пересчитывает успешный скоринг и не перезапускает завершённую заявку.
- Ручное возобновление имеет новую техническую попытку и аудит; дубли команды и конкуренция с worker не создают параллельных цепочек.

**Готовность:** работают запрос → документы → ответ → новая ревизия → повторное рассмотрение, временный сбой с автоповтором и исчерпание попыток с явным восстановлением сотрудником.

## 8. Проверить надёжность и соответствие контракту

Тесты добавляются по мере реализации. На этом этапе выполняется общая проверка собранного backend.

| Уровень | Что проверяем |
| --- | --- |
| Бизнес-правила | Матрица переходов и действий, ограничения продуктов, объединение уточнений, шкала заглушки, отсутствие автоматического решения |
| PostgreSQL integration | Атомарная подача/ответ/решение, rollback, уникальность, CAS версии, захват и возврат job, устаревший lease, конкурентная ротация и отзыв |
| API и контракт | Все 38 операций, схемы и статусы ошибок, отсутствие `null`/лишних полей, денежные строки, UTC, пагинация, multipart, заголовки auth и скачивания |
| Разграничение доступа | Чужие компании и вложенные ID, права owner/representative/bank_employee, отсутствие банковских данных в клиентских ответах и истории |
| S3 integration | Upload/download, ограничения файлов, недоступность хранилища, сбой между S3 и commit, защита исторических документов и очистка сирот |
| HTTP end-to-end | Полный путь до выдачи, отказ сотрудника, альтернативные условия, отказ клиента, уточнения, сбои и повторы, перезапуск worker, жизненный цикл сессии |

Интеграционные проверки используют PostgreSQL 16 и LocalStack, а не SQLite или только моки репозиториев. Для worker нужны управляемые timeout/lease и детерминированные сценарии, чтобы проверять восстановление без длительного ожидания.

Логи API/worker содержат request/application/job/snapshot ID. Наблюдаемость показывает failed/retry/blocked jobs и просроченные lease; журналы не содержат пароли, токены и содержимое документов. Аудит отказов в доступе сохраняется отдельно от откатываемой бизнес-транзакции.

**Готовность:** все обязательные сценарии воспроизводятся на чистом запуске, конкурентные команды сохраняют инварианты, структурированный контракт совпадает с реализацией. Временный сбой заглушки виден сотруднику и восстанавливается.
